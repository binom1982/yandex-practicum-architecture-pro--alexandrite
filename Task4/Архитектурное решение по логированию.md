# Архитектурное решение по логированию

## Необходимые логи (уровень INFO)

| **Система** | **Событие**                                   | **Данные для логирования**                                                    |
| ------------------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Shop API                 | Создание заказа                              | время, ID покупателя, номер заказа, сумма                                |
| Shop API                 | Загрузка 3D-файла                             | время, ID заказа, размер файла, формат                                      |
| Shop API                 | Изменение статуса заказа             | время, номер заказа, старый статус, новый статус                 |
| CRM API                  | Подтверждение заказа                    | время, номер заказа, ID менеджера                                              |
| CRM API                  | Получение сообщения из MQ              | время, тип сообщения, ID заказа                                                  |
| MES API                  | Расчёт стоимости                            | время, номер заказа, количество полигонов, время расчёта |
| MES API                  | Назначение оператора                    | время, номер заказа, ID оператора                                              |
| MES API                  | Изменение статуса производства | время, номер заказа, статус, ID оператора                                |
| RabbitMQ                 | Публикация сообщения                    | время, топик, ID сообщения, ID заказа                                          |
| RabbitMQ                 | Получение сообщения                      | время, топик, ID сообщения, результат обработки                    |
| Shop DB                  | Запись заказа                                  | время, номер заказа, операция                                                   |
| MES DB                   | Обновление статуса                        | время, номер заказа, статус, операция                                     |

## Дополнительные уровни логирования

| **Уровень** | **Когда используется**                                                             | **Примеры**                                                                                                                               |
| ------------------------ | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| INFO                     | Нормальная работа системы                                                          | Создание заказа, изменение статуса, успешные API вызовы                                                    |
| WARN                     | Предупреждения, не требующие немедленного вмешательства | Медленные запросы (>2с), повторные попытки отправки в MQ, близкое исчерпание лимитов |
| ERROR                    | Ошибки, требующие внимания                                                         | Неудачные API вызовы, ошибки БД, потеря сообщений в MQ                                                          |
| DEBUG                    | Отладка (только в dev)                                                                      | Детали запросов, внутренние состояния, SQL-запросы                                                             |

## Мотивация

Почему нужно добавить логирование:

1. **Снижение времени на разбор инцидентов** — сейчас проблемы разбираются со слов клиента, что занимает много времени
2. **Уменьшение нагрузки на поддержку** — специалисты смогут самостоятельно анализировать логи
3. **Проактивное обнаружение проблем** — возможность настроить алертинг до того, как клиенты начнут жаловаться
4. **Улучшение наблюдаемости системы** — понимание потока заказов через все системы

**Технические и бизнес-метрики:**

| **Метрика**                                      | **Тип**       | **Ожидаемое влияние**      |
| ------------------------------------------------------------- | ---------------------- | ------------------------------------------------ |
| Время разбора инцидента (MTTR)           | Техническая | Снижение с часов до минут   |
| Количество обращений в поддержку | Бизнес           | Снижение на 30-50%                     |
| Время обнаружения проблемы            | Техническая | Снижение с дней до минут     |
| Процент потерянных заказов            | Бизнес           | Снижение до <0.1%                      |
| Время реакции на аномалии               | Техническая | Снижение с часов до секунд |

## Приоритет внедрения логирования и трейсинга

Поскольку команда не может реализовать всё одновременно, предлагаю следующий порядок:

| **Приоритет** | **Система** | **Обоснование**                                                                                                                                             |
| ---------------------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1                            | MES API + MES DB         | Основная проблема — заказы «зависают» в производстве, операторы жалуются на медленную работу |
| 2                            | RabbitMQ                 | Критично для отслеживания потери сообщений между системами                                                               |
| 3                            | Shop API                 | Точка входа заказов, важно для отслеживания проблем с новыми заказами                                             |
| 4                            | CRM API                  | Важно для работы менеджеров, но менее критично чем производство                                                        |
| 5                            | Shop DB + MES DB         | Дополнительная наблюдаемость за данными                                                                                                  |

## Предлагаемое решение

### Технологии

| **Компонент**     | **Технология** | **Обоснование**                                                                                     |
| -------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| Сбор логов              | Filebeat/Fluentd               | Лёгкие агенты, минимальное влияние на производительность           |
| Хранение и анализ | OpenSearch                     | Apache License 2.0, хорошая масштабируемость, встроенный анализ               |
| Визуализация         | OpenSearch Dashboards          | Интегрировано с хранилищем, гибкие дашборды                                    |
| Алертинг                 | OpenSearch Alerting            | Встроенная возможность, не требует дополнительных компонентов |

### Архитектура решения

1. **Агенты сбора** устанавливаются на каждый инстанс (EC2)
2. **Централизованное хранилище** — отдельный кластер OpenSearch
3. **Дашборды** для каждой системы + общий дашборд потока заказов
4. **Алертинг** на критические события

### Политика безопасности

| **Аспект**                    | **Решение**                                                                                                                               |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Чувствительные данные | Маскирование персональных данных (email, телефон, адрес) перед отправкой в хранилище |
| Доступ к логам                | Только сотрудники с ролью «Поддержка» или «Разработчик» через SSO                                |
| Шифрование                      | TLS для передачи логов, шифрование хранилища                                                                        |
| Аудит доступа                 | Логирование всех запросов к системе логов                                                                          |

### Политика хранения

| **Параметр**        | **Значение**                                                            | **Обоснование**                                       |
| --------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Индекс                      | Отдельный индекс под систему (shop-logs, mes-logs, crm-logs) | Упрощение управления и поиска                |
| Срок хранения         | 90 дней для INFO, 30 дней для DEBUG                                     | Баланс между полезностью и стоимостью |
| Размер                      | Ожидается 50-100 GB/день при текущей нагрузке          | Планирование инфраструктуры                  |
| Холодное хранение | Архивация в S3 после 30 дней                                       | Снижение стоимости хранения                   |

### Превращение в систему анализа логов

**Алертинг:**

| **Событие**                     | **Порог**             | **Действие**                                                                               |
| -------------------------------------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Ошибки API                             | >10 за 5 минут            | Уведомление в корпоративный мессенджер, создание тикета |
| Потеря сообщений MQ           | >0 за 10 минут            | Уведомление команде, алерт в PagerDuty                                           |
| Медленные запросы            | >5с для 20% запросов | Уведомление команде разработки                                               |
| Аномальный рост заказов | >1000% за минуту         | Алерт безопасности (возможная DDoS)                                            |

**Поиск аномалий:**

1. **Базовая линия** — построение нормального профиля нагрузки по времени суток и дням недели
2. **Отклонения** — автоматическое обнаружение отклонений от базовой линии
3. **Корреляция** — связывание аномалий между системами (например, рост ошибок в MES после проблем в MQ)

## Критерии выбора технологии для работы с логами

| **Критерий**         | **ELK (Elastic)**                                            | **OpenSearch**                                | **Splunk**                              | **Loki**                             |
| ---------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------- | --------------------------------------------- | ------------------------------------------ |
| Лицензия                   | Elastic License (ограничения)                           | Apache 2.0 (открытая)                       | Проприетарная                    | AGPL v3                                    |
| Стоимость                 | Бесплатно (с ограничениями)                 | Бесплатно                                  | Дорого ($/GB)                           | Бесплатно                         |
| Масштабируемость   | Хорошая                                                     | Хорошая                                      | Отличная                              | Хорошая                             |
| Интеграция с Kubernetes | Хорошая                                                     | Хорошая                                      | Хорошая                                | Отличная                           |
| Функции анализа      | Богатые                                                     | Богатые                                      | Очень богатые                     | Базовые                             |
| Плюсы                         | Зрелая экосистема, много интеграций | Открытая лицензия, форк Elastic | Мощный анализ, поддержка | Лёгкий, для cloud-native          |
| Минусы                       | Ограничения лицензии                            | Меньше интеграций чем Elastic    | Высокая стоимость             | Меньше функций анализа |

**Выбор: OpenSearch**

**Обоснование:**

1. Открытая лицензия Apache 2.0 — нет рисков ограничений в будущем
2. Достаточный функционал для текущих задач компании
3. Бесплатно — важно для растущего стартапа
4. Хорошая масштабируемость — соответствует планам роста нагрузки
5. Совместимость с инструментами Elastic — можно использовать существующие знания команды
