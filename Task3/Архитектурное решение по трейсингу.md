# Архитектурное решение по трейсингу

## Анализ системы и C4-диаграммы

Системы для приоритетного покрытия трейсингом:

* Shop API (SpringBoot) — точка входа заказов
* CRM API (SpringBoot) — управление статусами
* MES API (C#) — расчёт цены и назначение операторам
* RabbitMQ — шина сообщений между сервисами

## Данные для трейсинга

| **Категория** | **Поле**            | **Описание**                                                        |
| ---------------------------- | ----------------------------- | --------------------------------------------------------------------------------- |
| Идентификаторы | `order_id`                  | Уникальный номер заказа                                      |
|                              | `correlation_id`            | Сквозной ID для отслеживания цепочки вызовов |
|                              | `user_id`/`api_client_id` | Источник запроса (клиент или внешний API)          |
| Контекст             | `service_name`              | Имя сервиса, обработавшего событие                  |
|                              | `operation`                 | Тип операции (create_order, calculate_price и тд)                   |
|                              | `timestamp`                 | Время события                                                         |
|                              | `status`                    | Результат: success / error / timeout                                     |
| Детали                 | `error_message`             | Текст ошибки при сбое                                           |
|                              | `duration_ms`               | Длительность операции                                         |
|                              | `queue_name`/`topic`      | Для сообщений RabbitMQ                                                |
|                              | `model_complexity`          | Количество полигонов (для расчёта цены)          |

## Мотивация

**Зачем внедрять трейсинг:**

* Позволит быстро локализовать, на каком этапе «завис» заказ, без ручного сбора логов
* Сократит время реакции на инциденты и нагрузку на поддержку
* Даст прозрачность для внешних клиентов API. B2B-клиенты смогут получать информацию о статусе и прогрессе обработки их запросов.
* Поможет выявить узкие места в производительности

**Технические метрики:**

| **Метрика**                                                                                                  | **Что означает**                                                                                                                                 | **Зачем нужна**                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| MTTR (Mean Time To Resolution) -**скорость реакции на сбои**                                   | Среднее время от обнаружения инцидента с заказом до его полного устранения                        | Показывает эффективность реакции команды: чем ниже MTTR, тем быстрее восстанавливается нормальная работа                         |
| Процент потерянных сообщений в RabbitMQ - **надёжность доставки**     | Доля сообщений, которые не дошли до потребителя или попали в DLQ                                                | Индикатор надёжности асинхронной коммуникации: рост метрики сигнализирует о проблемах в очередях или потребителях   |
| P95/P99 latency сквозного процесса - **стабильность производительности** | Время, за которое 95%/99% заказов проходят весь цикл обработки (от создания до расчёта цены) | Показывает реальную производительность системы для большинства пользователей; помогает выявлять «хвосты» задержек |

**Бизнес-метрики:**

1. Уровень удовлетворённости клиентов (NPS / CSAT)
   * В условиях роста на 100 заказов/мес. и расширения через API, потеря даже 5–10% клиентов из-за плохого опыта = значительные убытки.
   * Улучшение NPS/CSAT напрямую влияет на повторные покупки и сарафанное радио — критично для премиум-сегмента ювелирных изделий.
2. Процент заказов, выполненных в срок
3. Количество обращений в поддержку по статусу заказа

## Предлагаемое решение

### Технологии

* **OpenTelemetry** — стандарт для инструментирования (поддержка Java, C#, JS)
* **Jaeger** или **Zipkin** — бэкенд для хранения и визуализации трейсов
* **OTel Collector** — агрегация и экспорт трейсов из всех сервисов
