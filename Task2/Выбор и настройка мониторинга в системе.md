# Выбор и настройка мониторинга в системе

## Мотивация

В текущей ситуации Яндекс Метрика не покрывает backend-процессы, что критично после открытия API. Бизнес сталкивается с потерей заказов, задержками производства и жалобами API-клиентов.

**Внедрение мониторинга позволит:**

1. **Снизить потерю заказов:** Оперативно выявлять проблемы в очереди сообщений (RabbitMQ) и API.
2. **Повысить стабильность MES:** Выявить узкие места, вызывающие долгую загрузку дашборда операторов.
3. **Обосновать ресурсы:** Предоставить бизнесу данные о нагрузке для планирования масштабирования.
4. **Ускорить реакцию:** Автоматические алерты вместо жалоб от клиентов.

## Выбор подхода к мониторингу

1. **API сервисы (Shop API, CRM API, MES API):** Метод **RED** (Rate, Errors, Duration).
   * *Обоснование:* Сервисы запрос-ориентированные. Важно знать количество запросов, долю ошибок и время ответа.
2. **Инфраструктура (Базы данных, Инстансы приложений):** Метод **USE** (Utilization, Saturation, Errors).
   * *Обоснование:* Важно контролировать утилизацию ресурсов (CPU, Memory, Connections) для предотвращения исчерпания лимитов.
3. **Очередь сообщений (RabbitMQ):** Специфические метрики очереди.
   * *Обоснование:* Критично для отслеживания потока заказов между CRM и MES.

## Метрики и настройка

### 1. RabbitMQ

| **Метрика**                   | **Зачем нужна**                                                                                                 | **Ярлыки**      |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| `Number of dead-letter-exchange letters` | Выявление потерянных сообщений (заказов). Критично для бизнес-метрик. | `queue_name`,`exchange` |
| `Number of message in flight`            | Контроль backlog. Рост указывает на проблемы потребителей (MES/CRM).                 | `queue_name`              |

### 2. API (Shop, CRM, MES)

| **Метрика**     | **Зачем нужна**                                                                                                              | **Ярлыки**                             |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `Number of HTTP 500`       | Индикатор стабильности сервиса. Рост сигнализирует о багах или сбоях.             | `service`,`endpoint`,`method`                |
| `Response time (latency)`  | Контроль производительности. Особенно критично для MES API (жалобы операторов). | `service`,`endpoint`,`percentile (p95, p99)` |
| `Number of requests (RPS)` | Оценка нагрузки. Помогает планировать масштабирование.                                       | `service`,`endpoint`                           |

### 3. Базы данных (Shop DB, MES DB)

| **Метрика**                       | **Зачем нужна**                                                                                                              | **Ярлыки** |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| `Number of connections`                      | Предотвращение исчерпания пула соединений.                                                             | `db_instance`        |
| `CPU %`/`Memory Utilisation`               | Контроль утилизации ресурсов инстанса БД.                                                                | `db_instance`        |
| `Number of DB errors` (deadlocks, rollbacks) | Выявление сбоев транзакций, которые могут вести к потере данных или заказов. |                        |

### 4. Дополнительные метрики

| **Метрика** | **Зачем нужна**                                   | **Ярлыки** |
| ------------------------ | ----------------------------------------------------------------- | ---------------------- |
| `Size of S3 storage`   | Контроль роста хранилища 3D-моделей. | `bucket_name`        |

## План действий

1. **Развертывание TSDB:** Поднять инстанс Prometheus (или Managed Prometheus в Yandex Cloud) для хранения временных рядов.
2. **Инструментация сервисов:**
   * **Внедрить клиентские библиотеки Prometheus в Shop API (Java), CRM API (Java), MES API (C#).**
   * **Настроить экспортеры для PostgreSQL и RabbitMQ.**
3. **Визуализация:** Развернуть Grafana. Создать дашборды:
   * **Общий статус системы (Health Check).**
   * **Детальный дашборд по MES (для анализа проблем операторов).**
   * **Дашборд по очередям (для отслеживания заказов).**
4. **Настройка алертинга:** Настроить правила алертинга в Alertmanager (email/telegram) для критических метрик.

## Показатели насыщенности (Дополнительно)

| **Параметр** | **Пороговое значение**                   | **Действие при превышении**                                                                    |
| -------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `HTTP 500 Rate`          | **> 1% от общего RPS в течение 5 мин** | **Алерт в канал поддержки, создание инцидента.**                               |
| `CPU % (API/DB)`         | **> 80% в течение 10 мин**                     | **Алерт DevOps-инженеру, проверка необходимости масштабирования.** |
| `Dead-letter messages`   | **> 0 в течение 1 мин**                        | **Критический алерт архитектору/тимлиду (риск потери заказов).** |
| `Response time (MES)`    | **p95 > 5 сек**                                        | **Алерт команде разработки MES (приоритет на оптимизацию).**            |
